## Core product rules

1. **I write the program myself, every week.** No AI generation. A week is a mutable draft until I publish it. There is a "paste program" flow: I paste plain text like `1 Incline Dumbbell Press 3 x 8-12` and it parses into structured exercises, fuzzy-matched against the exercise library, with a review step for unmatched lines. "Copy last week" duplicates a published week.
2. **Weeks are versioned, not overwritten.** Logged sets always keep the loads/reps as performed, so history survives a program change.
3. **Goal: lose fat, keep muscle.** Nutrition targets derive from profile (weight, height, age, sex, activity) → TDEE (Mifflin-St Jeor × activity) → deficit → protein floor at 2.2–2.4 g/kg. Training days get +250 kcal from carbs.
4. **Nutrition is a full meal plan + grocery list**, not just macro logging: 7-day plan of meal slots → recipes → ingredients, and the grocery list is generated by aggregating ingredients across the week's meals, grouped by category, with per-item checked state.
5. **Body photos are private, no extra PIN.** Private Storage bucket, signed URLs generated server-side, 60s expiry. Never a public bucket.
6. **Allergies/excludes are hard filters** — a recipe containing an excluded ingredient never appears in plans, swaps or search.

### League scoring (implement as pure functions in `lib/league.ts`, unit-tested)

- **Consistency**: 120 pts per completed session (cap 5 sessions/week) + 10 pts per set with `is_complete`.
- **Transformation** (goal-relative so a cut and a bulk compete fairly): `% bodyweight moved toward goal × 200` (cut: loss counts, bulk: gain counts, recomp: |change| < 0.5% counts as +0.5) + `waist cm lost × 40` + `+150 if avg est. 1RM of top-3 lifts ≥ 100% of season start`. Uses 7-day averages of `body_metrics`, never single weigh-ins.
- Only percentages and points are ever visible to others — never kg, cm or photos. Standings are served by a `league_standings(season_id)` SECURITY DEFINER function that computes from each member's own rows and returns aggregates only.
- Seasons are 12 weeks; scores recomputed nightly by a Supabase cron into `league_scores` so the standings page is a single select.

**RLS**: enable on every table. Owner policy pattern — `using (user_id = auth.uid())` for the user-owned tables; for child tables (`program_days`, `program_exercises`, `set_logs`, `meal_plan_entries`, `grocery_items`, `recipe_ingredients`) check ownership through the parent with an `exists (...)` subquery. `exercises` and `ingredients`: `select` allowed when `owner_id is null or owner_id = auth.uid()`; writes only when `owner_id = auth.uid()`. Storage bucket `progress-photos` is private with a policy keyed on `(storage.foldername(name))[1] = auth.uid()::text`.

Write migrations in `supabase/migrations/`, plus a seed with the exercise library (start from the ~40 movements in the Upper/Lower program, public-domain photos from free-exercise-db), ~30 ingredients and ~15 recipes, and my week 12 program as an example.

## Conventions

- Server Components fetch data; Client Components only where there is interaction (session logging, drag-reorder, photo slider, checkboxes)
- One Server Action file per domain (`app/actions/program.ts`, `session.ts`, `body.ts`, `nutrition.ts`), each action zod-validated and `revalidatePath`-ing
- All weights stored in kg, all lengths in cm; convert at the display edge based on `profiles.unit_system`
- Dates: store `date` for anything day-scoped (weigh-ins, photos, plans) — never timestamps, to avoid timezone drift
- No `any`. Generate DB types with `supabase gen types typescript` into `lib/database.types.ts`
